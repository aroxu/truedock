# TrueNAS 25.10 capability matrix

This matrix is implementation routing, not a claim that every flow is complete.

| Area | Read baseline | Mutation baseline | Initial state |
| --- | --- | --- | --- |
| Connection | `system.info`, `system.product_type`, `core.get_methods`, `auth.me` | `auth.login_ex`, `auth.login_ex_continue`, `auth.logout` | Login, OTP, CE 25.10 minimum validation, and method discovery implemented. Signing out calls `auth.logout` before closing the socket, because dropping the transport alone leaves the authenticated session alive until it times out; the call is skipped when no transport remains and its failure never blocks the local teardown. Device-data reset makes local teardown authoritative immediately and performs logout/transport cleanup as bounded best effort, so an unresponsive server cannot trap the reset page. The account name comes from `login_ex` `user_info.pw_name` and falls back to `auth.me` when that object is absent (an API-key login can return SUCCESS without it), so the saved-server list is never unlabelled; a missing name never fails an otherwise good connection. Saved sign-in explicitly requests system authentication before Keychain/Keystore retrieval. One app-wide TrueDock PIN can protect opted-in credentials: Argon2id derives a key and AES-256-GCM protects each server with an independent salt, nonce, and server-bound associated data. The PIN is verified locally before any server connection and is never stored. Optional Biometric Unlock uses a protected copy when the platform supports it. A forgotten PIN leads to a typed full-device reset that removes every local TrueDock profile, credential, trusted certificate fingerprint, PIN/biometric copy, and app setting while never changing TrueNAS server data |
| Alerts/jobs | `alert.list`, `core.get_jobs` | `alert.dismiss`, `alert.restore`, `core.job_abort` | Reads and capability-gated alert dismiss/restore implemented; job center with active/failed/completed filters, progress, timing, log excerpts, and confirmed `core.job_abort` implemented for jobs the server marks `abortable` |
| Pools/disks | `pool.query` (including `topology` and `scan`), `disk.query`, `disk.temperatures` | `pool.scrub.scrub` start/pause/resume/stop, `pool.export`, `pool.offline`, `pool.online`, create/update/attach/replace | Pool and disk inventory, flattened vdev topology, live scrub progress, scrub start/pause/resume/stop, member offline/online, and pool export/destroy implemented; every destructive path is capability-gated and routed through the shared confirmation, with pool export/destroy requiring the pool name to be typed. Attach a disk to a mirror or stripe vdev (`pool.attach`, job) and replace a member with a new disk (`pool.replace`, job) implemented with a candidate-disk picker, vdev selection, force option for replace, and high-impact confirmation naming the pool, disk, and resilver consequence; the topology parser now carries the enclosing vdev GUID needed for `target_vdev`. Disk temperatures are read through `disk.temperatures` for the disks the inventory actually returned, because 25.10 removed the entire `smart.*` namespace and an empty device list would make the server poll every disk it knows. The reading is judged against each drive's own reported maximum and critical thresholds rather than a fixed number, a drive TrueNAS could not read stays "unavailable" instead of rendering as 0 °C, the over-temperature state is carried by text and weight as well as colour, and a failed or ungated temperature read never degrades the disk inventory. Pool create (`pool.create`, job) implemented with a topology editor supporting stripe/mirror/raidz1/raidz2/raidz3 data vdevs and optional cache/log/spare/dedup/special vdevs, encryption/dedup/autoTrim toggles, candidate-disk filtering against disks already in a pool, redundancy warnings for stripes, and a high-impact confirmation naming the disk count, redundancy level, and encryption key-management consequence; no update flow is exposed because `pool.update` is deprecated in favor of dataset-level editing |
| Dataset quotas | `pool.dataset.get_quota` | `pool.dataset.set_quota` | Implemented. Dataset-wide `quota`/`refquota` already live in the properties editor; this answers the different question of who may consume how much, which is what matters once a dataset is shared. The two halves of the API disagree and the disagreement is load-bearing: `set_quota` accepts `USER`/`USEROBJ`/`GROUP`/`GROUPOBJ`, but `get_quota` rejects the `*OBJ` variants outright, so a file-count limit is *written* under its own `quota_type` and *read back* as an `obj_quota` field on the plain row. The domain model separates the subject from the two limits it carries so that asymmetry does not leak into call sites, and one edit expands into up to two wire entries. Zero is the API's own way to remove a limit, so an untouched field is omitted rather than sent as zero - sending it would silently clear an existing limit. Two server refusals are mirrored locally to explain themselves rather than surface a raw EINVAL after a round trip: uid 0 cannot be given a user quota, and an unknown account is rejected (both confirmed live). Every account that has ever written appears whether limited or not, so the sheet sorts configured quotas above usage-only rows. Reaching the limit counts as over quota because ZFS refuses writes at it, not past it. Removal is `high`, not `critical`, and says the limit can be set again and nothing stored is deleted |
| Datasets | `pool.dataset.query` (including `origin`), `filesystem.getacl` | `pool.dataset.create`/`update`/`rename`/`delete`/`promote`, lock/unlock, `filesystem.setacl` | Read, filesystem and zvol create, POSIX1E/NFS4 ACL management, and reviewed property editing (comments, quota, refquota, readonly, compression, sync) with explicit inherit-vs-override handling, capability-gated rename, typed-confirmation delete, and lock/unlock implemented. Delete counts affected child datasets, snapshots, and shares before proceeding and is blocked for pool roots; unlock accepts a passphrase or hex key and force-unmount is an explicit option. Zvol creation is implemented through the same `pool.dataset.create` method as a separate call rather than a flag, because the payloads barely overlap: a volume sends `volsize` and `sparse` and must not send `share_type`, which applies only to a filesystem. The sheet shows only the fields belonging to the selected kind, takes the size in GiB because a byte count is unusable on a phone keyboard, and omits `volblocksize` unless chosen so the server keeps the default appropriate to the pool geometry. This is what lets an iSCSI disk extent be backed by a volume created in TrueDock rather than only one made in the web UI. Clone promotion is implemented via `pool.dataset.promote`. A clone depends on the snapshot it came from, which blocks deleting that snapshot or its dataset; promoting reverses the ownership so the clone owns the shared data. The dataset model reads `origin` and treats only a non-empty value as a clone, because ZFS reports an empty string for an ordinary dataset rather than omitting the property. The action is capability-gated on `pool.dataset.promote` and offered only for a dataset that is actually a clone, and its confirmation names the origin snapshot, states that the dependency reverses so the origin becomes deletable, and notes that no data is copied or deleted but space accounting moves to the promoted dataset |
| Snapshots | `pool.snapshot.query` | `pool.snapshot.create`/`delete`/`clone`/`rollback`, update/hold/release | Recent snapshot reads, explicit-name create, non-destructive clone with path validation, typed-confirmation delete, rollback, and hold/release implemented. Rollback makes the recursion choice explicit (fail if newer snapshots exist, destroy newer snapshots, or destroy newer snapshots and their clones) and counts the newer snapshots that would be destroyed; hold/release surface the held state from `pool.snapshot.query` |
| Data protection | replication, `pool.snapshottask.query`, `pool.scrub.query`, `cloudsync.query`, and `rsynctask.query` | `pool.snapshottask.create`/`pool.snapshottask.update`/`pool.snapshottask.run`/delete, replication/cloud-sync/rsync configuration, `replication.run`/`cloudsync.sync`/`rsynctask.run`/`pool.scrub.scrub`/abort | Reads, reviewed periodic snapshot create/edit/manual-run flows with `update_will_change_retention_for` impact preview, replication, Cloud Sync dry-run or sync, Rsync, and manual scrub Jobs implemented; capability-gated delete for periodic snapshot, replication, cloud-sync, and rsync tasks implemented through the shared high-impact confirmation. Replication task create/edit is implemented via replication.create/replication.update against the documented schema (name, direction PUSH/PULL, transport SSH/SSH+NETCAT/LOCAL, ssh_credentials, source_datasets as a list, single target_dataset, recursive, auto, enabled, retention_policy SOURCE/CUSTOM/NONE with lifetime_value/lifetime_unit sent only for CUSTOM, also_include_naming_schema, and a cron schedule sent only when auto is on); ssh_credentials is omitted entirely for LOCAL and the editor blocks a local task whose target is also one of its sources. Rsync task create/edit is implemented via rsynctask.create/rsynctask.update (path, user, direction, mode SSH/MODULE, desc, remotehost, remoteport defaulting to 22 for SSH and 873 for module, remotepath for SSH mode or remotemodule for module mode, ssh_credentials, enabled, validate_rpath, schedule), emitting only the remote field that matches the selected mode. Both editors select an existing SSH connection from keychaincredential.query filtered to SSH_CREDENTIALS and distinguish "no connections configured" from "could not read credentials"; TrueDock intentionally does not create SSH connections because that involves private-key material. Create and edit both route through the shared high-impact confirmation naming the write target and the overwrite consequence. Cloud-sync task create/edit is implemented via cloudsync.create/cloudsync.update against the documented schema (description, direction PUSH/PULL, transfer_mode SYNC/COPY/MOVE, path, credentials as an integer id, attributes carrying the remote location, schedule, transfers, encryption/filename_encryption/encryption_password/encryption_salt, and enabled): the attributes object is built per provider, sending bucket plus folder for bucket-based providers (S3, B2, Google Cloud Storage, Azure Blob, OpenStack Swift, Storj) and folder alone otherwise, with storage_class emitted only for S3. Credentials are selected from cloudsync.credentials.query and the editor distinguishes "none configured" from "could not read credentials"; TrueDock does not create cloud credentials because that involves provider secrets and OAuth flows. Encryption secrets are write-only: they are sent only on save, never stored or logged, and an edit that leaves them blank keeps the existing server-side secret. The editor reloads the task through cloudsync.query before editing and round-trips provider-specific attributes and unsurfaced top-level fields (notably pre_script/post_script, which run arbitrary server commands and are intentionally left to the web UI) while dropping runtime-only fields such as job and locked. Create and edit both route through the shared high-impact confirmation, which names the side that loses data: SYNC deletes at the destination, MOVE deletes the source after transfer, and COPY deletes nothing |
| Shares | `sharing.smb.query`, `sharing.smb.presets`, `sharing.nfs.query`, `sharing.webshare.query`, `iscsi.portal.query`, `iscsi.initiator.query`, `iscsi.target.query`, `iscsi.extent.query`, `iscsi.targetextent.query` | `sharing.smb.share_precheck`/create/update/delete, `sharing.nfs.create`/update/delete, iSCSI portal/initiator/target/extent/association create/update/delete, and ACL operations | Reviewed SMB and NFS creation/editing implemented with typed-confirmation delete; SMB share ACL replace (sharing.smb.get_acl + sharing.smb.set_acl) implemented with principal selection from local users/groups, allow read/change/full and deny roles, review step, and high-impact confirmation naming the server, target, and consequences; complete iSCSI topology reads and reviewed portal, initiator, CE iSCSI target, disk/file extent, and LUN association creation/editing implemented with server choices and name validation, plus capability-gated delete for portals, initiators, targets, extents, and associations; CHAP credential management is implemented: iscsi.auth.query is read into the resource model, and iscsi.auth.create/update/delete are surfaced through a dedicated CHAP credentials manager with a write-only secret editor (one-way and mutual CHAP, edit leaves secrets unchanged unless rotated), with create/update/delete each routed through the shared high-impact confirmation naming the user, the consequence to initiators/target groups, and that secrets are sent only over the authenticated session and never saved or logged; new target groups can now select a CHAP auth method (one-way or mutual) and assign an existing CHAP credential entry, while existing authenticated groups remain preserved (managed through the CHAP credentials manager); WebShare is intentionally read-only because 25.10 exposes query only |
| Apps | `app.query`, `catalog.apps`, `catalog.trains`, `catalog.get_app_details`, `docker.status`, `docker.config`, `app.upgrade_summary` | `app.create`/update/`app.upgrade`/start/stop/redeploy/rollback/delete | Installed-app start/stop, reviewed native catalog installation and upgrade Jobs, searchable discovery, Docker summaries, and capability-gated redeploy/rollback/remove implemented. Remove goes through a review sheet for image and volume retention, then a critical typed-confirmation naming the app; redeploy and rollback use the shared high-impact confirmation. Rollback is version-aware: it loads the same `app.upgrade_summary` the upgrade sheet uses, presents a target-version picker (current running version flagged), shows release notes for the chosen target, then submits `app.rollback` with `[appId, {'app_version': version}]` — the documented two-argument shape — rather than a bare `[appId]` that the middleware would reject. The picker seeds on the first non-current advertised version so a real rollback target is preselected. Capability-gated reconfiguration (`app.update` + `app.config` + `catalog.get_app_details`) is implemented: the installed app's live config seeds the catalog question editor, the app instance and version are locked, and the new values are sent through `app.update` as a job; custom apps without a catalog reference are detected and the reconfigure action is hidden with an explanatory message |
| Instances | `virt.instance.query`, `virt.instance.device_list`, `virt.global.config`, `virt.global.pool_choices`, `virt.instance.image_choices` | `virt.instance.create`/`update`/`delete`/`start`/`stop`/`restart`, `virt.global.update` | 25.10's container and VM surface, and the one that actually exists on the baseline: `virt.*` replaced the standalone `container.*` methods, which 25.10 does not advertise at all. A coverage audit found all 33 `virt.*` methods uncovered while the app gated on `container.query`, so the section could never appear on a supported server. Instances are gated on `supportsVirtInstances` independently of `supportsContainers`, so a server exposing either surface gets the matching UI. `virt.global.config` is read before the list because the platform is unusable until a storage pool is chosen and the server answers an empty list in that state, which is indistinguishable from "no instances"; TrueDock explains the difference and offers pool selection behind a high-impact confirmation naming the pool, since the hidden `.ix-virt` dataset lands there and moving it later means recreating every instance. Identifiers are instance *names*, not numbers. Stop and restart send `{timeout, force}`: a graceful stop uses a bounded timeout so a wedged guest cannot hang the job, while force power off sends `timeout: -1`, which the schema documents as meaningful only with `force`. Update sends only changed fields because the method merges a partial object, so resending everything would overwrite `raw` and the userns idmap that TrueDock does not surface. Creation validates the name as a DNS label before sending, since Incus derives the guest hostname from it and rejects anything else with an opaque middleware dump; memory is collected in MiB and sent in bytes, and a pinned CPU set such as `0-3` is accepted alongside a plain core count. Deletion destroys the instance root disk, so it is a typed critical confirmation |
| Containers/VMs | `vm.query`; discovered 26+ `container.query`, `container.device_choices` | `vm.start`/`vm.stop`/`vm.restart`/`vm.poweroff`, `container.start`/`container.stop`/`container.restart`, configuration and device operations | VM and standalone-container inventory plus confirmed lifecycle control implemented; every verb is hidden unless the discovered method list exposes it, stop/restart/power-off require an impact-named confirmation, and forced power off is separated from a graceful stop; VM configuration editing is implemented via vm.update (name, description, sockets/cores/threads, memory and minimum memory, autostart, bootloader, CPU mode, guest time, shutdown timeout, ensure display device), sending only the changed fields so untouched values stay at their server default, with a high-impact confirmation naming the VM and the restart-to-apply consequence; VM device management is implemented via vm.device.query/create/update/delete with a device list, add and edit forms for the common disk/CD-ROM/NIC/display cases, and high-impact confirmation for add/edit/remove that names the VM, notes disk removal does not delete the underlying zvol, and warns that repointing a disk changes which storage the guest boots from. Editing seeds from the current attributes and preserves the ones the form does not surface (controller type, sector size, boot order, NIC bridge), because TrueNAS replaces the attribute set rather than merging it; clearing the MAC field removes the key so the server regenerates one instead of being sent an empty value. Edit is gated on vm.device.update independently of create and delete; container configuration editing is implemented via container.update (name, description, autostart, vCPUs, memory limit), preserving the raw device/volume/environment lists it does not surface so the round-trip keeps them, with a high-impact confirmation naming the container and the restart-to-apply consequence; container device assignment is implemented via container.device_choices: existing devices are listed with derived labels and can be removed, and new block devices can be attached from the server-provided choice list using the 25.10 passthrough shape, with the updated device list sent back through container.update so TrueNAS replaces the whole configuration; the full config is reloaded through container.query before editing to capture the preserved lists |
| Services | `service.query` | `service.control`, `service.update` | Read and start/stop implemented. Start-on-boot is implemented separately via `service.update` (`enable`), because `service.control` changes only the current run state and is forgotten on reboot; the row addresses the service by its record id rather than its name, keeps the two mutations on independent busy keys so one cannot mask the other, and routes the change through the shared high-impact confirmation stating that the boot setting changes but the service is neither started nor stopped now. The control is capability-gated on `service.update` and the boot state stays visible as information when the method is absent |
| Active sessions | `auth.sessions` | `auth.terminate_session`, `auth.terminate_other_sessions` | Implemented. API keys answer what *could* connect; this answers what is connected right now, which is the question that matters when an account may be compromised, so it sits beside the key list rather than in its own screen. Three details are load-bearing. The account name lives inside `credentials_data`, not at the top level, so reading the obvious field yields unlabelled sessions. The server mixes its own internal UNIX-socket connections into the same list - five of six on an idle test server - and those are the middleware talking to itself, not root logins; they are filtered out but their count is reported so the visible list cannot silently disagree with the server. And `secure_transport` is treated as insecure when absent, because defaulting an unknown to "encrypted" would hide precisely the case the UI flags. TrueDock's own session is labelled and deliberately not terminable here: ending it only signs the app out, which Sign out does more clearly, and offering it beside other sessions invites a mis-tap that disconnects the user instead of the intruder. Ending all others uses `auth.terminate_other_sessions` rather than a loop, because the server excludes the caller and a client-side loop would race its own connection. Both actions are `high` rather than `critical` - nothing stored is lost - and the confirmation says the holder can sign in again, so ending a session is not mistaken for locking an attacker out. Ages are shown coarsely since phone and server clocks differ |
| Accounts | `user.query`, `group.query`, `api_key.query`, privilege queries | `user.update`, `group.update`, `api_key.delete`, create/delete and privilege management | User and group reads, reviewed `user.update`/`group.update` editing, and reviewed create/delete implemented, covering full name, email, shell, SMB, password-disabled, lock, auxiliary groups, group name/SMB, and membership; built-in and directory accounts are non-editable, only changed fields are sent, and delete optionally removes the user's primary group. Capability-gated password change is implemented through `user.update` (`password` field): a dedicated review sheet validates length and confirmation, then the shared high-impact confirmation names the account and states that active sessions may be ended and the password is sent only to the server. Privilege management is implemented in the dedicated Privileges surface described below. API key management is implemented: `api_key.query` is read into the account section and `api_key.delete` revokes a key, which is the independent withdrawal that makes API-key authentication preferable to a password in the first place. The model carries no key material because TrueNAS returns the secret only once at creation, so TrueDock can identify and revoke a key but never display it. Revoked and expired are kept as separate facts: one was withdrawn deliberately, the other simply ran out, and both are reported as unusable. Revocation is withheld for an already revoked key rather than offered as a no-op, is capability-gated on `api_key.delete`, and uses a typed critical confirmation stating that every client using the key stops working immediately (including TrueDock itself if it is that key) and that the key cannot be recovered. Key creation is intentionally left to the web UI because the resulting secret is shown once and would need to be handled outside the app |
| Network | `interface.query`, `staticroute.query`, `interface.commit_node`, `interface.commit`/`interface.checkin`/`interface.rollback`, `staticroute.create`/`staticroute.update`/`staticroute.delete` | staged changes, check-in, commit/rollback | Interface and static-route reads implemented; static-route create/update/delete implemented through a reviewed editor with CIDR/gateway validation, capability-gated per-row edit and delete, and a high-impact confirmation that names the destination and states the change is staged until the network workflow runs; the network commit/checkin/rollback workflow is exposed through a dedicated sheet that walks the user through commit (job), verifying the connection survived, and check-in (locks the change) or rollback, with each stage surfaced explicitly so a broken network configuration cannot be silently committed; interface address/MTU/DHCP editing is implemented via `interface.update` against the documented schema (description, ipv4_dhcp, aliases as {address, netmask as an integer CIDR prefix, type INET/INET6}, and an optional mtu): the editor reloads the configured values through `interface.query` filtered by id so it edits the configured rather than merely the live state, clears aliases entirely while DHCP is on, omits mtu when unset so the server keeps its default, validates addresses/prefixes/duplicates/MTU range, warns when another interface already owns DHCP because 25.10 permits DHCP on only one interface, and warns that switching to DHCP drops the existing static addresses; a save routes through the shared high-impact confirmation naming the interface and the new addressing, then hands straight off to the commit/checkin sheet so a staged change is never left to expire silently Global network settings are implemented on top of `network.configuration.config`/`update` and `network.general.summary`. The read distinguishes configured values from the ones actually in effect: the response's nested `state` object holds what the system is using, and on DHCP the configured gateway and nameservers are empty strings while `state` carries the lease. Showing only the configured side would make a working server look unconfigured, and showing only the effective side would make a lease look like a saved setting, so both are labelled. Updates send only changed fields, because the method merges a partial object and resending everything would rewrite `activity` and `service_announcement` that TrueDock does not surface. An empty string is the documented way to clear a gateway or nameserver, so a blank field is valid rather than malformed. Unlike an interface edit this applies immediately, with no commit/check-in window to roll it back, so an edit that would clear a routing value the server is currently using escalates from a high-impact confirmation to a typed critical one naming the host. |
| Service settings | `ssh.config`, `smb.config`, `nfs.config`, `ftp.config`, `snmp.config` | `ssh.update`, `smb.update`, `nfs.update`, `ftp.update`, `snmp.update` | Implemented as one generated editor rather than five sheets: all five surfaces are the same shape — read a flat object, send back only what changed — and hand-writing them separately is how one ends up sending a field the others don't. The exposed fields are a documented subset declared in `serviceFields`; everything omitted keeps its server value because every one of these `update` methods merges a partial object, which a live probe verifies field by field. Matching a service row to its editor needs an explicit map, since the `service.query` name is not always the API namespace (SMB is `cifs`). Shared secrets — the SNMP community string and the v3 password and privacy passphrase — are never prefilled from the response and are sent only when the user types one, so a stored secret is never overwritten with a blank and none reaches the screen. `community` was also added to the log redactor: SNMP v1/v2c authenticates with it despite the name. Nullable choices send null rather than an empty string to unset them, as `v3_privproto` documents. A running service restarts to apply a change, so the confirmation states whether clients are interrupted now or the change waits for the next start |
| Cloud backup | `cloud_backup.query`, `cloud_backup.list_snapshots` | `cloud_backup.create`/`update`/`delete`/`sync`/`abort`/`restore`/`delete_snapshot` | Implemented as a surface distinct from cloud sync despite sitting beside it: this is a restic-style repository with snapshot retention, so it carries a repository password, a `keep_last` count, and browsable snapshots that a sync task has no equivalent for. The repository password is the only field in the app that is required on create and means "unchanged" when left blank on an edit: `cloud_backup.query` does return it, but seeding the editor would put a credential on screen and risk sending a placeholder as the real password, which would leave the repository unreadable — so the stored value is read back solely to resend it, and never reaches `CloudBackupConfiguration`. `credentials` arrives as an integer on the way in and an expanded object on the way out, so both shapes are accepted. A real run is confirmed because it costs provider bandwidth and request charges; a dry run changes nothing and is offered without one |
| Alert policies | `alert.list_categories`, `alertclasses.config` | `alertclasses.update` | Implemented as a merge of two reads, because neither is sufficient alone: `alert.list_categories` is the catalog of every class the server can raise along with its default severity, while `alertclasses.config` returns *only* the classes an administrator overrode — an empty map on a stock server. Listing just the overrides would render an empty screen while hiding all 115 classes that could be changed, so the effective policy is computed per class and a missing entry means "at its default". Delivery defaults to `IMMEDIATELY` when unset. `alertclasses.update` replaces the whole override map, so the editor returns the full merged configuration and the payload is rebuilt from it; sending one class would silently reset every other override. The payload also carries only classes that differ from their default, so a stock class is never pinned as an override forever — a live probe asserts both directions. Classes set to `NEVER` are called out in the list and named as a consequence in the confirmation, because nothing else in the app reveals that an alert will never reach any destination however severe it becomes |
| Configuration backup | `core.download` wrapping `config.save` | `config.reset` | Implemented. `config.save` writes to a job pipe that a JSON-RPC client cannot read — calling it directly answers `Pipe 'output' is not open`, verified live — so it is wrapped in `core.download`, which returns a job id plus a tokenized HTTPS path. `buffered: true` is sent because the unbuffered mode blocks the job until a client reads or 60 seconds elapse. The app opens the tokenized URL in the platform browser through `url_launcher`, with link copy as a fallback; the browser owns the download destination and TrueDock does not claim completion it cannot observe. The path is resolved against the server's base URI rather than concatenated, so a non-default port still yields a valid URL, and the token proved single-use: a second fetch answers 401. The payload is *not* an archive unless extra material is requested — a plain backup is the SQLite settings database itself, confirmed by downloading it — so the suggested filename uses `.db` and only switches to `.tar` when the secret seed or pool keys are included. Those options are not neutral checkboxes: the seed decrypts stored credentials and the pool keys unlock encrypted datasets, so each says so and selecting any raises a warning that the archive must be stored like the server password. `config.reset` reverts every share, user, task, and network setting with no undo, so it takes a typed confirmation naming the server and sends `reboot` explicitly rather than relying on the server's default of true |
| Audit log | `audit.query`, `audit.config` | `audit.update` | Implemented. The audit log is the record of every action the rest of the app can take, so it closes the loop on the mutation surfaces rather than adding a new one. `audit.query` is the only query method that nests everything in a single object with hyphenated keys (`services`, `query-filters`, `query-options`) instead of the usual positional `[filters, options]`, so it does not share the common query helper. Timestamps arrive in two forms — `timestamp` as `{"$date": millis}` and `message_timestamp` as bare epoch seconds — and the wrapped form is preferred because it is unambiguous about units. A `METHOD_CALL`'s `method`, `description`, `authenticated`, and `authorized` live inside `event_data` while `success` is top level, so both levels are read. Denial (`authorized: false`) is modelled separately from plain failure: being refused permission and attempting something that broke are different answers to "what happened". Results are ordered newest first, since an audit log is read backwards from the most recent event and the server's default order is the opposite. Retention editing lives in its own sheet rather than inline, because shortening retention destroys recorded history; only changed fields are sent, so an untouched threshold is never resent |
| Privileges | `privilege.query`, `privilege.roles` | `privilege.create`/`update`/`delete` | Implemented. Users and groups say who exists; privileges say what any of them may administer, so this belongs beside Accounts. `local_groups` is expanded into full group objects on read but takes bare gids on write, so both the ids to send and the names to display are kept. Roles compose — 74 of the 141 the test server advertises declare `includes` — so the catalog is read alongside and the effective grant is resolved rather than showing only the literal list; the resolver tolerates a cyclic catalog. `FULL_ADMIN` and the web shell are both treated as unrestricted access, because the shell runs as root and bypasses whatever the role list restricts, and either escalates the confirmation to a typed one. A privilege with no roles and no shell is rejected locally: the server accepts it, which makes it look configured while granting nothing. The three built-in privileges cannot be deleted, so that action is absent rather than offered and failing, their name is not editable, and narrowing one is named as a lockout consequence |
| Alert destinations | `alertservice.query` | `alertservice.create`/`update`/`delete`/`test` | Implemented for all ten destination types the schema declares. The attribute form is generated from `alertServiceFields` because the API discriminates `attributes` on a `type` string and validates against one exact variant: a hand-built form per destination would eventually send a key belonging to another variant, which fails the whole call. Switching type therefore discards the previous attributes rather than carrying them. Credentials are never prefilled on screen, but they cannot simply be omitted on an edit either — `alertservice.update` rejects the call with "field required" for a variant's required secret, verified live — so a blank field substitutes the value from the queried entry, which does return secrets in plaintext. Telegram's `chat_ids` is parsed into an integer array rather than sent as typed text, and webhook URLs are validated locally because the server enforces `format: uri` with an opaque error. A destination whose type TrueDock does not model is still listed, read-only, with an explanation rather than being dropped. `alertservice.test` takes a whole configuration rather than an id, so the sheet offers a test before saving: a wrong webhook or token only fails at delivery time |
| Alert email | `mail.config`, `mail.local_administrator_email` | `mail.update`, `mail.send` | Implemented. `MailConfiguration` deliberately has no password field: `mail.config` does return `pass`, so modelling it would create a leak surface for logs, screenshots, and state dumps, and TrueDock holds the password only for the single update that sets it. The editor's password field starts empty and is sent only when the user types one, since resending the whole object would overwrite the stored password with a blank. Two live-verified server constraints shape the payload: `mail.update` rejects the entire call with "fromemail: this field is required" when that field is absent *and* not already stored, so a first-time configuration cannot be a pure partial update and `fromemail` is always included in that case; and the server refuses an empty `fromemail`, so once set it cannot be unset from the app. Enabling SMTP authentication with a username but no password (and none already stored) is rejected locally, because the server accepts it and then silently fails to authenticate, which would stop alerts arriving with no error anywhere. A test send is offered right after saving, since validation cannot prove delivery works — a wrong password or a blocked port only surfaces on a real send |
| Scheduled commands | `cronjob.query` | `cronjob.create`/`update`/`delete`/`run` | Implemented with the shared `TaskSchedule` object, because `cronjob` takes the same `{minute, hour, dom, month, dow}` payload the snapshot, replication, rsync, and cloud-sync tasks use; the preset control and schedule summary were extracted into `TaskScheduleLocalizations` so two pickers cannot drift into describing the same schedule differently. The API states its output flags negatively — `stdout: true` *suppresses* stdout from the mailed report — so the domain type stores "capture" and inverts on the wire; exposing the raw field would make the switch read as the opposite of what it does, and a live probe asserts the round trip. `cronjob.run` sends `skip_disabled: false`, because the server default silently does nothing for a disabled job the user explicitly asked to run, which TrueDock would then report as success. Running a job executes arbitrary shell with the configured account's privileges, so it takes a high-impact confirmation naming the server and that account rather than a bare tap |
| System | system info/settings/`update.status`, `boot.environment.query` | `system.reboot`, `system.shutdown`, `update.run`, `update.config`, `update.update`, `boot.environment.activate`/`keep`/`destroy`, config workflows | System info, one-second update-status refresh, alerts, live job views, and typed-confirmation restart/shutdown/update are implemented. Each disruptive confirmation counts running apps, VMs, and in-flight jobs, states that TrueDock loses its connection, and skips the post-action refresh because the session ends. General settings are a page rather than a modal and edit hostname, timezone (choices loaded from `system.general.timezone_choices`), and syslog level through `system.general.config`/`system.general.update`; the unsupported description fields were removed after the 25.10 server rejected them as extra inputs. Power actions live on General. Update profiles use the server's DEVELOPER, EARLY_ADOPTER, and GENERAL choices; custom firmware upload and its file picker were deliberately removed. Boot environments live under Advanced, where `boot.environment.query` and capability-gated activate/keep/destroy provide the recovery path from a bad update. TrueDock distinguishes the running environment (`active`) from the one selected for the next boot (`activated`) and warns when they differ. Activation changes only the next boot and never silently reboots; destroy is a typed critical confirmation and is never offered for the running or next-boot environment. Pool and share data are explicitly outside a boot environment. These mutations invalidate the system resources provider so pending state becomes visible immediately. System tunables are deliberately not exposed in the UI. |

High-risk entries remain gated by the confirmation policy in `AGENTS.md`. Exact
payload shapes are checked against the captured 25.10 schema by the release gate;
the Phase 5 audit links the implemented surfaces to their live probes and tests.

High-risk and irreversible operations share one confirmation surface
(`lib/core/widgets/destructive_confirmation.dart`). It always names the server and
the target and lists concrete consequences derived from currently loaded
resources rather than generic warnings. `MutationImpact.critical` additionally
disables the action button until the user types the exact target name, so pool
destruction, dataset deletion, snapshot deletion, rollback, restart, shutdown,
and updates cannot be triggered by a single mis-tap.

Reporting uses `reporting.netdata_get_data` over a bounded one-hour window for the
Overview sparklines. The overview requests CPU, RAM, load, each advertised
network interface, and each advertised disk identifier. Interface and disk
cards swipe horizontally when the server exposes more than one identifier.
The 25.10 `disk` graph reports read/write throughput in KiB/s rather than
operation counts, so TrueDock labels it Disk I/O instead of inventing an IOPS
value. Netdata rows arrive as `[timestamp, ...dimensions]` and may contain
nulls; TrueDock preserves those gaps as breaks in the line instead of drawing
an invented value through them, prints the current value as text, and labels
the range so the charts never depend on colour alone.

Catalog installation targets the 25.10 response shape: `catalog.get_app_details`
returns a `versions` mapping whose entries contain normalized `schema.groups`,
`schema.questions`, and initial `values`. TrueDock renders the middleware-supported
string, text, integer, boolean, IP address, URI, path, host path, dictionary, and
list types; evaluates `show_if`; keeps hidden defaults; masks private fields; and
sends the resulting values only in the secret `app.create.values` object. Unknown
question types block review instead of being silently discarded.
